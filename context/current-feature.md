- The demo user's identity is intentionally fixed/known (`demo@devprep.io`, name "Demo User", `12345678` hashed via `bcryptjs` at 12 rounds), not mirrored from `mockUser`'s `jordan.reyes@email.com` — everything else on the row (role, location, phone, links) still comes from `mockUser`. NextAuth isn't wired up yet, so nothing can log in with it today; the hash exists so this account is ready the moment credentials auth lands.
- Rather than hand-transcribing ~60 records into `prisma/seed.ts` by hand (high transcription-error risk, and permanently drifts from the UI's own source of truth), the seed script directly imports `src/lib/mock-data`'s arrays and transforms each record into a `prisma.<model>.upsert()` call — this also replaced the old hardcoded `skillTaxonomy` object literal (which only existed to re-encode `src/lib/mock-data/skills.ts` a second time) with the same imported `skillCategories`/`skills` arrays, removing a duplication/drift risk that already existed before this feature.
- Idempotency strategy: entities with a real natural unique key (`Skill`, `SkillCategory`, `CVTemplate` by name; `SkillBankEntry`/`JobPostRequirement` by their compound unique constraints) upsert on that key as before. Entities with no natural key (`Experience`, `Project`, `Certification`, `JobPost`, `UnresolvedRequirement`, `Comparison`, `CV`, `CVVersion`) are instead upserted by an explicit `id` set to the mock record's own string id (e.g. `"exp-lumen"`) — Prisma's `@id @default(cuid())` only auto-generates an id when none is supplied, so this is a legitimate way to get deterministic, human-readable, idempotent primary keys for seed data, and it means FK fields between these entities (e.g. `Project.experienceId`, `CV.latestVersionId`) can reuse the mock ids directly with no separate id-lookup map needed. Verified idempotent by running `db:seed` twice in a row and confirming row counts didn't change the second time.
- `Comparison.gaps` is recomputed fresh per the spec (not copied verbatim from the mock's frozen JSON) — `currentLevel`/`severity`/`skillName` are derived live from whichever `SkillBankEntry` rows actually got seeded, using `LEVEL_RANK`-based comparison against each gap's `requiredLevel`. One real spec ambiguity surfaced here: the spec said to join against `JobPostRequirement` rows, but only `job-acme` has any (by design, to preserve the "couldn't detect requirements" empty state for the other 5 posts) — joining strictly against `JobPostRequirement` would've produced empty `gaps` arrays for 5 of the 6 comparisons. Resolved by using each mock comparison's own gap list as the required-skill/level input (still recomputing `currentLevel`/`severity` live), which keeps every comparison's gap data meaningful without requiring every job post to have structured requirements.
- `CVVersion.contentHash` and `renderedFileUrl` are computed/set for real rather than copied from the mock's placeholder strings — `contentHash` via `crypto.createHash("sha256")` over the version's actual `content`, `renderedFileUrl` always `null` (matches `architecture-notes.md`'s "populated lazily on first export only" rule).
- `Prisma`'s `Json` input types require an index signature that the project's own `CVContent`/`ComparisonGap[]` interfaces don't declare — surfaced as a real `npm run build` type error (`Type 'CVContent' is not assignable to type ... Index signature ... is missing`), not just a lint nit. Fixed with a small `toJsonInput(value: unknown): Prisma.InputJsonValue` bridge cast in `seed.ts`, rather than loosening those interfaces or using `any`.
- `scripts/test-db.ts`'s Step 2 checks reuse `getCertificationExpiryStatus` from `src/lib/certifications-data.ts` (already built for the Certifications screen) rather than re-deriving the 60-day-window logic, and assert on real structural facts rather than just presence: the demo user + password hash round-trip via `bcryptjs.compareSync`, Skill Bank FK joins resolve, Experience↔Project links resolve both directions, all 4 certification expiry states are actually present, Acme has both confirmed and unresolved requirements while at least one other post has none, every comparison's gaps span all 3 severities, and every CV's `latestVersionId` matches its highest `versionNumber`.
